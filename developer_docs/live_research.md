# Step 6: ライブWeb調査・証拠収集（試作）

## 実行

```sh
python3 -m afternoon_tea.research --max-shops 1
python3 -m afternoon_tea.research
python3 -m unittest discover -s tests -v
```

標準ライブラリのみ、APIキー不要。実行日と調査対象は日本時間。後者は店舗マスター70件の探索を試みます。
コマンドは対象サイト・検索エンジンの `robots.txt` とアクセス制限を守り、リクエスト間隔を最低1秒空けます。
エラーはログに保存し、429/403/CAPTCHAを回避する処理は実装しません。取得先の利用規約と運用条件も事前に確認してください。

## 実際に行うこと

- 各店を 一休 → 食べログ → TableCheck の順で検索。
- 許可された公開ページを取得できた場合は、ATの記載・予約表現・価格らしき表現を抽出。
- 取得したURL、確認日、抜粋、失敗理由を監査JSONに保存。
- 日本時間の開始日から40日先までのデータスケルトンを生成。
- `.staging/research-YYYY-MM-DD/audit.json` と `data_YYYY-MM-DD.json` を保存。

## 重要な制約

**この試作はWeb検索・取得の調査基盤であり、公開に必要なプラン検証器ではありません。**
「アフタヌーンティー」「予約」「円」という文字が同じページ内にあっても、
ATプランの通常価格・提供期間・事前予約ボタン・ランチ/朝食の条件はまだ確認できません。
そのため現段階での `confirmed_shops=0` は意図的であり、公開可能な新HTMLは作りません。

自動検索は検索エンジンのrobots設定や応答形態の変化で0件になることがあります。
`audit.json` に成功・失敗を記録し、0件を「店舗なし」と解釈しません。
元のマスター70店舗以外の網羅探索、新規候補の昇格、提供日・予約の実検証、1店複数プラン、
14エリアの新店探索などは**未実装**です。

また「未検証の候補をHTMLに出さない」と「全店調査を完了した」は別です。
`candidates=[]` は未検証店がゼロという証明ではありません。
調査できない店は `notes.status` と `audit.json` に全件列挙します。
全店の確認ができない限り、現在の正常な `docs/index.html` を維持します。

## 公開との分離

`docs/index.html`、既存の `deploy.yml`、`build_html.py`、
`research_spec.md`、保護ハッシュは一切変更しません。
すべての生成物はGit管理対象外の `.staging/` にしか保存しません。
ステップ7以降で、予約プランの厳密な確認と自動生成・公開ガードを実装する必要があります。

## 未検証候補をHTMLに残さないための次工程

1. 予約ページ内のATプランをページ単位で確認し、通常価格・日時・メニュー・予約導線を検証。
2. 検証できた店舗だけ `research.status=confirmed` に昇格。各フィールドの引用を保管。
3. 既存の未確認候補5店と毎週の新店探索について、確認不可なら公開せず、監査レポートだけに残す。
4. 全件実施状況を計測し、不完全な調査を「東京全店調査済み」と表示しない。
5. 公開前に既存validatorとHTML検証を行い、合格した場合のみサイトを更新する。
